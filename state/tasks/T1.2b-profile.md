## 1. 每帧模型调用结构(task 1)

`run_step`(agent_simlingo.py:668)→ 每帧 **1 次** `self.model(model_input)`,但内部(`DrivingModel.forward`,driving.py:104,`predict_language=True` 硬编码,driving.py:58)展开为:

| 步骤 | 内容 | 位置 |
|---|---|---|
| ① adaptor embed | prompt token embedding 查表(含 512 个 `<IMG_CONTEXT>` 占位) | adaptors.py |
| ② 视觉编码 | InternViT-300M 前向 2 tiles(448²)+ mlp1 投影,替换占位 embedding | internvl2_model.py:114 `extract_feature` |
| ③ **贪心文本生成** | `greedy_sample`(llm.py:178):逐 token **全序列重算**,`max_new_tokens=100`,eos 早停 | llm.py:217 循环 |
| ④ driving 前向 | prompt+已生成 token+30 个 driving query(20 route+10 speed)**整序列再前向一次**,取末 30 位过 MLP head → cumsum → waypoints | driving.py:154-162 |

**关键事实:生成不是白送的旁支,它在决策路径上** —— ③ 生成 token 的 embedding 被回接进 ④ 的输入
(driving.py:155 `torch.cat((input_embeds, inputs_driving...))`),waypoints 条件于生成文本。
官方 README/论文([CVPR'25 paper](https://arxiv.org/abs/2503.09594))无任何"评测时关语言输出"的说法;
`predict_language=True` 在代码里硬编码、无配置项,`start_eval_simlingo.py` 也不改它 —— **官方评测路径就是带逐帧生成**。
`predict_language=False` 分支(driving.py:177)是**另一条决策路径**(driving query 直接接 prompt,无生成文本条件),属"改变模型行为",按任务约束只报告不实施。

③ 的 `greedy_sample` **完全没有 kv-cache**:每生成 1 个 token 都对 ~546–660 token 的完整序列重跑一次
Qwen2-0.5B(InternVL2-1B 的 LLM 实为 Qwen2-0.5B + LoRA r=32)。实测每帧生成中位 17 token(假数据;
真实场景有长生成,评测日志里 662 帧单帧 >2s、最长 4.67s,对应 ~30–100 token 触顶帧)。
即每帧 **18 次 LLM 全序列前向**(17 生成 + 1 driving)+ 1 次 ViT。

## 2. 每帧耗时拆分(离线实测,中位数;task 2)

| 段 | 耗时 | 占比 | 说明 |
|---|---|---|---|
| CPU 图像预处理 | 7 ms | ~0.5% | jpeg roundtrip(训练/测试一致性所需,**不能去**)+ crop + dynamic_preprocess + bicubic transform |
| CPU prompt 构建 | ~1 ms | ~0% | importlib 重载 conversation.py 0.46ms + 模板 0.01ms + tokenize 0.6ms(AutoConfig agent 已只加载一次) |
| 视觉编码 ② | 17.8 ms | ~1% | 2×448² tiles,InternViT-300M,flash-attn 生效 |
| adaptor embed ① | ~1 ms | ~0% | |
| **贪心生成 ③** | **1527 ms** | **~93%** | 17 token × ~85 ms/次 全序列前向 |
| driving 前向 ④ | ~85 ms | ~5% | 整序列(prompt+生成+30 query)重算 |
| **模型段合计** | **~1634 ms** | | 离线、带 sync 插桩;对照实测闭环 1.02–1.25 s/帧(同量级,差值=插桩+GPU 竞争波动) |
| metric_info dump | 1→97 ms | 随帧数线性增长 | 每帧 `json.dump` 全量重写递增 dict(agent_simlingo.py:794 `self.step % 1 == 0` 恒真);1000 帧 10ms、4000 帧 42ms、8000 帧 97ms;实测产物已达 597KB/路线 |

**为什么 85 ms/次前向这么慢**:`t12b_overhead_split.py` 实测 **enqueue=82.7ms vs wall=82.9ms** ——
GPU 完成速度与 CPU 提交速度一样快,瓶颈是 **Python 侧 dispatch**(24 层 × PEFT wrapper × FA2 varlen unpad 等
~2000+ 次算子调用),不是 GPU 算力,也不是 UE4 server 竞争。GPU 数学本身每次前向仅 ~4 ms 量级。
分解:`disable_adapter()`(去 LoRA 数学、留 wrapper)54ms;kv-cache 单 token step 41ms 且**与上下文长度无关**
(L=8/64/600 均 ~40ms)→ 每次前向 ~40ms 纯固定开销。

**flash-attn 确认生效**(无 eager fallback):
- LLM:`Qwen2FlashAttention2`,`config._attn_implementation = flash_attention_2` ✓
- ViT:`config.use_flash_attn=True` 且层上 `use_flash_attn=True` ✓,flash_attn 2.8.3 已装 ✓

**kv-cache 确认缺失**:见 §1③。eos 早停正常(tokenizer eos=`<|im_end|>`,生成中位 17 token 即停)。

**浪费的 lm_head 全序列投影**:`LLM.forward`(llm.py:133)走 `Qwen2ForCausalLM`,每次前向都计算
[1,~600,151655] logits(182MB bf16/次,18 次/帧 ≈ 3.3GB 显存 alloc churn),但 greedy_sample 只用
`features[:, -1]` 自己再算最后位置 logits(llm.py:227);driving head 的 `get_predictions` 也只取 features
(adaptors.py:163,logits 形参未用)。**全序列 logits 完全是死代码**。实测投影本身仅 1.9ms(CPU-bound 下
wall 收益≈0),价值主要在显存 churn。

## 3. 提速建议(未实施,补丁只给位置与思路;task 3)

### A. 严格合法(数值 bit 等价已实测验证)

| # | 位置 | 改动 | 收益 | 验证 |
|---|---|---|---|---|
| A1 | agent_simlingo.py:794-798 | metric_info dump 降频:`self.step % 50 == 0` + destroy() 时补写最终版 | 路线后段省 40–100ms/帧;一条路全程省 ~80–90s;产物最终内容不变(本来就是全量重写) | 纯 IO,无数值影响 |
| A2 | agent_simlingo.py:594-598 | conversation.py 模块对象缓存(setup 时 import 一次),消除每帧 exec_module | 0.46ms/帧 | 同一模块字节码,无差异 |
| A3 | llm.py:133-141 / driving.py:156 | LLM.forward 改走 backbone(`Qwen2Model`),只取 `last_hidden_state`;最后位置 logits 用现有 `F.linear`(greedy_sample 本就这么做) | wall≈0(CPU-bound),省 3.3GB/帧显存 churn,降低碎片/OOM 风险 | **实测 features 差 = 0.0,waypoints 差 = 0.0**(t12b_noise_isolate.py B1) |

A 合计:帧墙钟收益 ~2–5%(主要来自 A1 在路线后段),**不动大头**。

### B. 灰区(实测有效,但数值非 bit 等价,需拍板 + 闭环 A/B 后再上)

| # | 改动 | 实测/预估 | 数值风险 |
|---|---|---|---|
| B1 | **greedy_sample 加 kv-cache**(prefill 1 次 + 逐 token cache 解码;driving query 复用同一 cache 追加前向,省掉整序列重算) | **实测 1.92×**(模型段 1630→848ms;prefill 83 + 17×~39 + driving 追加 ~40);预计帧墙钟 1.22s→~0.7s(0.041×→~0.07× 实时) | 实测(t12b_kvcache_ab.py):5 帧假数据 4 帧生成文本完全一致、1 帧 token 翻转;waypoints max diff 0.25–0.9m(bf16 kernel 累加顺序差,经 cumsum head 放大)。**注意:换 GPU/batch/shape 本来也有同级噪声,但按"数值结果不变"严格口径它不满足** |
| B2 | setup 时 LoRA `merge_and_unload()` | 每次前向 83→~50ms,cached step 41→~25ms;叠加 B1 预估模型段 ~500ms,**总 ~3×**(220 路线墙钟按 T1.1 外推 ~75h→~25h) | bf16 权重合并舍入,与 B1 同量级 |
| B3 | torch.compile("reduce-overhead")/CUDA graph 消除 ~40ms/次的 Python dispatch | 理论上限再 3–5×(GPU 数学每次前向仅 ~4ms) | 动态 shape + FA2 varlen 下工程风险高;compile 融合改数值。**远景,只报告** |

### C. 决策路径类(只报告,不实施)

- `predict_language=False` 关生成:官方评测就是开着跑的(§1),关了 waypoints 输入条件变 → 结论不可比,禁止。
- `use_cot=True`(config_simlingo.py:9)改 prompt:同上,禁止。
- 去 jpeg roundtrip:训练/测试分布一致性要求,禁止。
- max_new_tokens 100→更小:会截断长尾帧的真实输出(实测有 28+ token 帧),改变行为,禁止。

### D. 顺手发现的正确性问题(非性能)

- agent_simlingo.py:867 `destroy()` 访问 `self.cfg.data_module.encoder`,但 .hydra/config.yaml 无此键 →
  **每条路线结尾都抛 `ConfigAttributeError` → "Failed to stop the agent"**(eval_attempt0.log:14116 等 20 处)。
  成绩已先注册、不受影响,但 cleanup 不干净(model 已 del 后才抛,内存回收没问题)。建议 `getattr` guard。

## 4. TickRuntime / RouteScenario_25845 线索(task 4)

**结论:不是单帧超时阈值,也不是代码死循环,是路线级 game-time 预算耗尽 + 车辆物理卡死。**

- 日志中**没有任何 TickRuntime/Watchdog 异常**。25845 段结尾(log:14072-14074):game time 恰好
  **200.000s** → `> Stopping the route` → 正常注册结果(FAILURE:RouteCompletion 41.94%、Collision 1 次、
  MinSpeedTest 189.03%)。200s = `RouteScenario._estimate_route_timeout()`(route_scenario.py:131,
  `SECONDS_GIVEN_PER_METERS=0.4` × 路长 ≈500m)。leaderboard `--timeout=600` 是 wall 秒级
  agent watchdog/ScenarioManager 超时,单帧实测最大 4.67s,远未触发。
- agent 全程稳定 tick:4001 帧 / 4872.66s = **1.218 s/帧**(ratio 0.041)。662 帧单帧 >2s(最长 4.67s)
  全部是长文本生成帧(§1③ 的 100-token cap),不是挂起。
- 直接原因:车辆被场景堵死/卡住。段末连续每帧 `force_move: 14`(agent_simlingo.py:774-781)=
  `stuck_detector > 800` 持续触发 creep(throttle 0.4)但速度仍 <0.1m/s(物理上动不了,MinSpeedTest 189%
  佐证全程低速)。恢复机制的时间尺度在慢推理下被放大:800 帧 stuck = 40s game ≈ **16 min wall**,
  force_move 仅 15 帧(0.75s game)。推理提速能压缩 wall 时间,但 game-time 尺度的卡住属驾驶行为问题,
  超出本任务范围(与 AccidentTwoWays 场景处理有关,建议 T1.2 复跑时单独看该路线的 viz)。

## 5. 总结论

1. 慢的根因坐实是**实现层**:`greedy_sample` 无 kv-cache,每帧 17–100 次 Qwen2-0.5B 全序列重算
   (占帧耗时 ~93%),且单次前向 ~85ms 是 **Python dispatch-bound**(enqueue=wall),GPU 利用率仅 ~5%。
2. flash-attn 双侧生效、EOS 早停正常、无重复编码 —— 这些"常见嫌疑"均排除。
3. **严格合法**(bit 等价)空间只有 ~2–5%(metric dump 降频 + 模块缓存 + lm_head 死代码)。
   大头提速(kv-cache 实测 1.92×、叠加 LoRA merge 预估 ~3×)数值上非 bit 等价
   (waypoints max diff 0.25–0.9m,5 帧中 1 帧 token 翻转),**是否采纳需用户拍板**;
   若采纳,先做 3–5 条路线的闭环 DS A/B 再全量。
4. 25845 的 FAILURE 与性能无关:车辆卡死耗尽 200s 路线预算;另发现 destroy() 每条路线抛
  ConfigAttributeError(无害但值得修)。
